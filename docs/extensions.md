# Login profiles and extensions

Bam hosts WebExtensions through WebKit’s extension engine (macOS 15.4 or later). This document records what the host provides, how packages reach it, what Bam adds on top of WebKit, and exactly which vendor behaviour has been observed. None of it establishes general Chrome, Firefox or Safari extension compatibility; every claim below names the package and the probe it comes from.

## Profiles

Manage Spaces assigns each Space a named login profile. Spaces assigned to the same profile share cookies, website storage, Favorites, history/recently closed pages, and extensions. Separate profiles use separate persistent WebKit data stores and extension controllers. The legacy Default profile retains the existing default website-data store; nothing copies authenticated pages or cookies into a new profile.

A same-profile move keeps the loaded page intact. A cross-profile move or reassignment asks before reloading affected pages. Cancel leaves the live pages alone and keeps the editor’s staged changes available. Accept uses a new renderer in the destination profile; unsaved edits and playback do not carry over. Peek, Little Bam, Split pairs, extension-created tabs and archive restoration retain their source profile. Profile deletion, import of browser cookies, and a user-facing private-window mode are not included.

The intended first setup is **Personal: Dashlane** and **Solo: Dashlane + 1Password**. The signed-in Dashlane observations below concern the separate persistent preview and do not establish both profile setups. A fresh profile starts signed out; account login belongs to the user through the extension/site UI.

## Getting an extension into Bam

Extensions → Manage Extensions offers three ways in. All of them end in the same reviewed import: the package is copied privately, size- and entry-capped, and its permissions and website access are shown before anything is enabled. Store archives receive the disclosed package preparation below; signed Safari bundles are preserved intact.

**Add Extensions** below the address bar opens Bam’s library directly. Type a name to search Chrome Web Store, Firefox Add-ons and Safari Mac App Store sources together, or paste a store / `.xpi`, `.crx` or `.zip` link. Popular entries appear on first open. Product icons and source marks keep origins visible; the main action adds the recommended installable build to the named profile, with permissions and technical details available separately. Choosing another source is explicit. Search is debounced, superseded requests cannot overwrite newer results, and failures are reported per source.

Firefox discovery uses Mozilla’s public API. Chrome discovery parses bounded JSON embedded in its public search page without executing page scripts: this is a best-effort adapter, not a supported Google catalog API, and page-schema changes can make Chrome search unavailable. Safari discovery uses Apple’s US Mac App Store catalog and only returns entries identified as Safari extensions or known exact product IDs. Results are bounded and are not an exhaustive worldwide inventory. Exact verified store IDs connect Dashlane, 1Password, vidIQ and Bitwarden; other cross-store grouping requires matching product name, publisher and homepage, and differing same-store IDs never merge.

Safari extensions ship inside containing apps. If the exact catalog app is already installed, a Safari result offers **Add to Bam** and imports its signed WebExtension after permission review. Otherwise it offers **Get from App Store**; return to Bam after Apple installs the app. The library refreshes on return. Apps containing multiple WebExtensions offer a Bam-themed choice. Apple’s acquisition step is still external. A store badge indicates provenance, not universal compatibility.

Downloaded packages are verified before they are unpacked: a Firefox Add-ons build must match the SHA-256 that Mozilla publishes for that file; a Chrome Web Store build must be a CRX3 whose every RSA publisher proof verifies and whose derived ID matches the listing. Direct links are fetched over HTTPS only and are marked as unverified in the manager. The manager row of every store-installed extension shows its source, publisher and how it was verified. These checks establish that the bytes are the ones the store published; they do not vouch for the publisher.

**Check for Update** asks the installed build’s own source for a newer version and, after confirmation, replaces the package in place. The extension keeps its identifier, so WebKit storage, grants and profile assignment survive; the update goes through the same permission review before it is enabled, and the previous package is restored if the new one fails to load. Bam never switches an installed extension from one store’s build to another’s: storage formats differ between a vendor’s Firefox and Chrome builds, so the other build is offered as a separate install instead.

**Import Folder…** installs an unpacked folder, as before. Folder imports are trusted executable code with no publisher verification. Safari catalog imports instead require the exact app bundle ID from Apple’s catalog, an Apple-anchored App Store signature and a matching signing team on the nested WebExtension. Bam snapshots the entire signed `.appex` without rewriting its resources and uses WebKit’s public bundle initializer. It revalidates the installed app and private snapshot before each load. Keep the containing app installed; after it changes, select **Refresh from Installed App** in Bam’s manager. This verifies the same app/extension/team offline, reviews permissions, and keeps the extension UUID and local storage. Disabled extensions stay disabled. A changed app that prevents startup is shown as **Not running** with a recovery action; failed updates roll back. Legacy Safari App Extensions and standalone content blockers use different formats and are not supported. Existing Safari sign-ins are not copied.

Enabled extensions appear below the main address bar with their real action icon, label and badge. Click an icon to open WebKit’s popup for the current tab; the puzzle menu includes overflow. With the sidebar collapsed, the macOS Extensions menu remains available. Tabs, Peek and Little Bam retain their profile scope; changing tabs/profiles dismisses stale popups. Popup ownership tracks the exact presentation so reopening an action does not discard its newly loaded web view. Repeating Add for the same source/build in a profile reuses it; a disabled copy offers Enable. Closing the library cancels installation before its commit boundary. Canceling an update permission review leaves the original extension running.

An extension is installed and enabled in one profile. To use the same package in another profile, install it separately there. Enable/disable/remove and permission revocation are available. Previously injected page code cannot be removed in place; Bam offers to reload affected pages, with Later as the safe default.

### Choosing a build

A product may exist as a Firefox build (HTML background page, MV2 or MV3 with `background.scripts`) and a Chrome build (MV3 service worker). Bam now provides its limited compatibility layer in both environments. The resolver retains a preference for the broader tested Firefox coverage; dated vendor observations explain the recommendation. Compatibility notes preserve known errors and untested workflows rather than presenting availability as full support. Runtime coverage and account workflows must still be assessed per build.

## What the host provides

WebKit supplies background/content scripts, extension storage, actions/popups, native context-menu actions and own-origin pages. Bam adds profile-filtered tab/window adapters, cold-start navigation gating, window creation/removal/state for `windows.create` (opened as a Little Bam window, including the extension’s own pages; an extension can close only windows it opened), tab zoom, `tabs.detectLanguage` (the page’s recognizable text, else its `<html lang>` or `<meta http-equiv="content-language">` — not the HTTP header — else `und`; never the user’s own locale). Unlike Chrome, which answers from browser state, Bam samples the page from an isolated world, so it needs access to that tab: a host grant or the tab’s `activeTab` grant. A sample is discarded if the tab, its document or the access changed while it was read, and tab snapshots for `tabs.captureVisibleTab` on pages the extension may access (including a tab’s `activeTab` grant). Every change of a tab’s loading state (start, finish, failure, stop) is reported, and a tab whose flag flipped and flipped back within one turn still gets its `tabs.onUpdated`, so the event carries `status: "complete"` once a page has loaded even when its URL is unchanged since commit; Dashlane’s sign-in security check (check.dashlane.com) waits for exactly that event before requesting its Turnstile token. Extension pages send the same Safari user-agent suffix as tabs, so an extension that fetches a site from its background (vidIQ reads YouTube pages this way) receives the same documents a tab would.

The 0.21 draft adds a limited external native-message transport for **only the verified Chrome Web Store build of 1Password** (`aeblfdkhhhdcdjpifhhbdiojplfjncoa`), targeting `com.1password.1password`. It needs a separate **Connect Desktop…** review in the manager. Old installs without structured CRX verification offer **Verify Desktop Support…**, which reacquires an equal/newer signed package from the same listing without changing its UUID/storage. Neither website permissions nor the internal worker bridge grant external desktop access.

The host must be the vendor-documented BrowserSupport executable inside the official, intact Apple-signed 1Password app, registered in Chrome’s standard native-host directory and authorizing the official extension origin. Bam pins the reviewed registration, executable and app signatures; host/app changes require review again. Bam itself must have an Apple-issued signature. It launches the exact helper directly, with bounded length-prefixed JSON and queues, at most four connections per extension and sixteen per profile. Every send/receive checks the exact loaded context, profile and current host grant. Revocation, disabling, package replacement and shutdown close owned helpers. Host stderr and message contents are not logged.

This is a transport implementation verified with original synthetic hosts, **not demonstrated 1Password pairing or Touch ID**. The current ad-hoc preview cannot pass the browser-signature gate. A proper signed build, the installed official desktop app and explicit trust in [1Password’s browser settings](https://support.1password.com/additional-browsers/) are still required. Safari containing-app handlers, Firefox-native 1Password and other desktop hosts remain unsupported. Bookmarks, history, identity and sessions namespaces remain masked.

### Compatibility layer

WebKit on macOS 27 lacks several namespaces that Firefox and Chrome builds call unconditionally: `notifications`, `idle`, `privacy`, `management`, `downloads`, `offscreen`, `fontSettings`, `commands`, `storage.managed`, plus members such as `runtime.getBrowserInfo`, `runtime.onSuspend`, `runtime.requestUpdateCheck`, `webNavigation.onCreatedNavigationTarget` and `action.getUserSettings`. For an extension whose manifest requests one of the bridged permissions (required permissions only; optional shim permissions are not yet provided), Bam installs a document-start script in that extension’s own origin (HTML background page, popup and options pages). The script defines only what is absent, keeps callback and promise styles, and talks to the host through an authenticated message handler; replies and events are evaluated in the exact frame that asked, so an extension page embedding another extension page cannot receive its answers.

What the layer does: notifications are delivered through macOS User Notifications when Bam runs as an app bundle, with click, button and dismiss events routed back; `idle.queryState` reads the system event source; `privacy` settings answer as read-only and not controllable; `management` describes the extension itself; `downloads.download` goes through Bam’s download coordinator for HTTP(S) URLs; `commands.getAll` reads the manifest; `storage.managed` is empty and read-only; `runtime.onUpdateAvailable` exists but never fires, because Bam has no pending-update state (updates are user-initiated in the extension manager, reviewed, and replace the extension directly; Bam does not download updates in the background); `scripting.ExecutionWorld` supplies the `ISOLATED`/`MAIN` constants WebKit's `scripting` lacks (its `executeScript` already accepts `world` as a string; what each world does remains WebKit's own behavior), only where WebKit exposes `scripting` and never replacing an engine enum; `fontSettings.getFontList` lists the Mac's installed font families (localized names, sorted by name; system-private families omitted), while the other `fontSettings` getters and setters reject because Bam has no per-script or default font settings; `getBrowserInfo` identifies Bam. Everything else in those namespaces rejects or is a no-op. A shimmed call that fails in callback form does not set `runtime.lastError`: WebKit's `runtime.lastError` is a native attribute a defined property cannot override, and the canonical measurement reads `null` in both an extension page and a worker. The callback runs without arguments and the error is logged; the promise form rejects with the error.

`offscreen` (`createDocument`, `closeDocument`, `hasDocument`, `Reason`) hosts one hidden page per extension: an extension-origin web view built from the extension's own WebKit configuration, so it is an ordinary extension page in the same profile and can message the worker with `runtime.sendMessage`. It is never put in a window or listed as a tab. `createDocument` resolves after the page has loaded, accepts only the extension's own URL, Chrome's reasons and a justification, and keeps the page's main frame on the extension origin. A second document is refused with Chrome's exact “Only a single offscreen document may be created.” (Bitwarden treats that message as success), and `closeDocument` without one reports “No current offscreen document.” The document closes on `closeDocument`, revocation, disable, update, uninstall, profile shutdown and quit, and if its web process ends; closing or revoking while it is still loading stops it at once (the pending `createDocument` rejects) instead of waiting for the load or its 30-second timeout, and a replacement is never affected by an earlier load's late outcome. `runtime.getContexts` now reports that document as `OFFSCREEN_DOCUMENT` (with its filters applied) and still lists no other contexts. Differences from Chrome: the document is a full extension page with every API the extension's other pages have (Chrome exposes only `runtime` there); any page of the extension may be used (Chrome expects a bundled static HTML file); reasons are validated but not enforced, so reason-specific lifetimes such as closing an `AUDIO_PLAYBACK` document after 30 seconds without audio are not implemented. Like Chrome's, it cannot be focused or shown. Other limits: a hidden page is subject to WebKit's normal throttling of views that are not on screen; clipboard, audio and media reasons get no extra privileges beyond what WebKit gives any page without a user gesture; an install reviewed before this bridge keeps working but cannot create documents until an update or re-enable review grants `offscreen`; a prepared worker receives the API through the adapter refresh described below. The permission review lists the bridged permissions under “Provided by Bam’s compatibility layer (limited)”, and the manager row repeats them.

WebKit’s namespace wrappers turned out to be weakly cached: members grafted onto `webNavigation` or `runtime` disappeared once nothing in the page referenced the wrapper, which made 1Password’s startup pass or fail from one launch to the next. The layer now holds each namespace object it extends and re-applies members for a while after load; two consecutive probes then started 1Password identically.

### Manifest V3 workers

Chrome-store and folder imports with a service worker receive an adapter in Bam’s private package copy, before the original worker code runs. Classic workers retain their original registration URL and use `importScripts` to load the adapter followed by a byte-identical saved source. Module workers use a sibling entry with static imports, preserving the original module URL and relative imports. Bam preserves the original manifest and a preparation record outside the package, verifies the saved source hash and exact generated bytes when preparation is repeated, and rejects unsafe or escaping paths. The source download/folder remains untouched. Existing disabled installations receive this preparation only through an explicit enable/review.

The worker adapter shares the document layer’s capabilities and calls a restricted native transport. Every call and event is bound to the loaded extension, controller, profile, declared capability and current reviewed grant. Revocation and disable stop this internal native access; the independently reviewed 1Password transport above has a separate gate. Notifications and idle changes use an event port, without timer-based worker keepalive. This is limited API support, not Chrome parity: runtime context enumeration, optional shim permissions, download lifecycle events and general external native handlers remain gaps.

### Explicit resource management symbols

JavaScriptCore on the macOS versions tested so far has no `Symbol.dispose` or `Symbol.asyncDispose`. TypeScript's `using` helper then throws “Symbol.dispose is not defined.”, and wasm-bindgen classes skip their dispose methods; Bitwarden's background and popup use both for its SDK client. Bam defines the two symbols, non-writable and only when absent, as the registry symbols `Symbol.for("Symbol.dispose")`/`Symbol.for("Symbol.asyncDispose")` so that, like real well-known symbols, every realm shares them (a resource made in a same-origin extension frame can be disposed by its parent), at the start of extension pages and prepared service workers, before any extension script. Engine-provided symbols are never replaced. Content scripts and websites are unchanged. A worker receives this through its prepared adapter (see the next section).

### Worker adapter refresh

A prepared service worker loads Bam's adapter from a file written into Bam's private copy of the package. That adapter carries the Bam version and API layer that wrote it, so each load compares it with the current Bam's adapter. The adapter is rewritten only when everything else the preparation recorded still verifies: the schema, the sidecar metadata outside the package, the manifest marker, the original-manifest hash, the relocated vendor script's SHA-256 and the exact entry loader. The installed adapter must also be byte-identical to the hash Bam recorded, or already equal to the new adapter after an interrupted earlier refresh, in which case only the metadata is repaired. Only that file and the external metadata change. Vendor scripts, the manifest, grants and extension storage are untouched, and the change is noted on the extension. A package that does not verify, including any edited adapter or symbolic link, is left byte-for-byte as it was and loads as it did before this refresh existed (the reason is logged). If a write fails after the adapter itself was replaced, the next load finds the new adapter with the old metadata and completes the record. Other preparation schemas are left to their own path, and signed Safari bundles are never prepared. The canonical Preview worker fixture passed in the `863da15` extension run (435 checks): for both classic and module workers, it first ran an observably older adapter with refresh disabled, then enabled refresh and required the current adapter version to execute. It also checked retained worker storage, unchanged grants and vendor bytes, and the update disclosure. This verifies those original fixtures, not every vendor package or WebKit version.

### Cookie change details

WebKit fires `cookies.onChanged` without its `changeInfo` argument (its own FIXME, webkit.org/b/267514), so Chrome-style listeners receive `undefined`. Grammarly's sign-in cookie watch then throws “Cannot destructure property 'cookie'”. For extensions that already have the `cookies` API, Bam overrides the listener methods of WebKit's own `onChanged` event object (WebKit's namespace attributes are native values a defined property cannot replace, as the first canonical run showed), keeps that event as the trigger, reads `cookies.getAll({})`, compares it with the previous snapshot and delivers `{removed, cookie, cause}` for each difference. Only cookies the extension can already read are compared. Limits: `cause` is inferred — `explicit` for additions and removals, a removed `overwrite` followed by an added `explicit` for a changed cookie, and `expired` when a removed cookie's expiry had passed; `evicted` and `expired_overwrite` are never reported. This is a best-effort state diff, not a complete cookie event stream: changes before a context's first listener has its baseline are not reported; an add-then-remove or several overwrites between two reads can coalesce or disappear; a cookie that becomes invisible to the extension (lost host access) looks like a removal; and partitioned cookies take part only when `getAll` returns them. Delivered cookies are copies. Each listener period has its own read sequence, and reads finishing after the last listener is removed are discarded. A listener removed during a dispatch is not called, and a comparison stops delivering as soon as a callback ends its listener period. Each context with listeners reads the cookie list on every change. Once an engine passes real `changeInfo`, Bam forwards those objects unchanged and stops diffing, including any comparison already in progress.

### declarativeNetRequest timing

WebKit applies an extension's declarativeNetRequest rules asynchronously after the extension loads. With uBlock Origin Lite's six default rulesets, requests in roughly the first 3–6 seconds after load were not filtered, and matching requests were blocked afterwards (root's canonical probe on a loopback page). Bam's start-up gating waits for extensions to load, not for their rules to be applied, and WebKit offers no public signal for that. Bam does not currently delay page loads to cover this gap.

### Static declarativeNetRequest rules: disclosure only

Bam cannot intercept WebKit's compilation of an extension's static rulesets, and the refusals above apply only to dynamic and session updates. Instead, Bam reads every declared ruleset of an installed extension once per extension version (and again if the audit format changes) and discloses how many rules use request-method conditions or exclude every resource type WebKit supports, by ruleset ID and whether that ruleset is on by default. It never shows rule text or URLs, never changes vendor files, rules or the enabled set, and notes that the extension can turn rulesets on or off at run time. Rulesets it cannot check safely (missing, outside the package, through a symbolic link, oversized, not a JSON rule array, or beyond 100 rulesets / 32 MB per file / 128 MB in total, counting every byte read) are named as unchecked. The audit runs off the main thread during load, so new installs, updates (audited before their review) and installs from an earlier Bam are covered; it is stored as its own record field and replaced rather than appended. In Manage Extensions the affected row says “Network rules: see details”, and the selected extension's details area (scrollable, selectable, focusable, labelled for VoiceOver) shows the warning first, then the preparation notes; installs from an earlier Bam get no new permission review, so the row marker is how the warning is found. Permission reviews show it first as well. Signed Safari WebExtensions are not audited.

### bookmarks: read-only getTree

Partial support, disclosed as such: for an extension that declares `bookmarks`, Bam defines `bookmarks.getTree()` and nothing else (no `create`/`update`/`move`/`remove`/`search`/`get*` methods and no events). It returns the extension's own login profile's saved items: a root (`id` "0") with a Favorites folder and then one folder per Space of that profile (`space-<id>`), holding its kept tabs and folders in sidebar order. Pages carry the address the user kept, not the page a tab has since navigated to; Today tabs, other profiles, Arc Easel references and non-http(s) pages are not included; a kept Split lists both pages. IDs are Bam's stable folder and tab IDs; `index`/`parentId` are real positions; no dates are given. Chrome's “Bookmarks Bar”/“Other Bookmarks” roots do not exist in Bam. Trees over 10,000 nodes or nested deeper than 32 are refused, never truncated.

Access needs an explicit grant: the permission review lists “bookmarks (read-only …)”, and installs reviewed before Bam provided it stay ungranted (Manage Extensions shows “Not granted: bookmarks …”; disable and enable the extension to review). Private windows are refused. Without a grant the call is refused natively on every call: the promise form rejects; the callback form logs the error and calls back with no argument (Bam cannot set `runtime.lastError`), never with an empty tree. WebKit's own `bookmarks` namespace, compiled in only conditionally and without public host support, stays hidden; if a future WebKit provides a working one, Bam's adapter steps aside.

### history: read-only search and genuine events

Partial support, disclosed as such: for an extension that declares `history` and was explicitly granted it at review, Bam defines `history.search(query)`, `history.onVisited` and `history.onVisitRemoved`, and nothing else (no `addUrl`, `deleteUrl`, `deleteRange`, `deleteAll` or `getVisits`). The data is the extension's own login profile's in-memory Bam history (at most 5,000 visits; web pages only; consecutive visits to the same page are one visit); other profiles and private windows are never included, and nothing is loaded from disk or the network at query time.
- `search` follows the official schema (`text` string required; `startTime`/`endTime` finite milliseconds; `maxResults` an integer from 0 to 2,147,483,647, Chromium's Int32 schema, default 100; `startTime` defaults to 24 hours ago; `null` members and array queries are refused, identically in the adapter and natively). Bam's documented subset: one item per URL with a visit at or after `startTime` and before `endTime`; `title` and `lastVisitTime` from that URL's latest visit; every whitespace-separated word must appear (case-insensitively) in title or URL — not Chrome's own matching; newest first (Chrome does not specify an order). `id` is the URL's SHA-256. `visitCount` and `typedCount` are not given (Bam does not keep true counts). Replies whose encoding would exceed 4 MiB are refused, not truncated; the size is counted from UTF-8 lengths (with JSON escapes) before any result is built, so a huge URL or title is refused without large allocations. 5,000 short records are about 0.7 MB.
- `onVisited` fires for each visit Bam's history accepts (including a revisit of the same page), with that URL's item, as soon as it is in memory (not a promise that it reached disk). `onVisitRemoved` fires with `{allHistory: true, urls: []}` after Clear History succeeds, and `{allHistory: false, urls}` when the 5,000-visit limit drops a URL's last visit. Startup loading fires nothing. Each event's encoded size is counted from UTF-8 lengths before it is built and bounded at 1 MiB: removed URLs are split across several `onVisitRemoved` events that each fit (every URL once, in order); a visit, or a single removed URL, too large for any event is not delivered — never truncated or replaced — and is recorded as a diagnostic in that profile (counts and sizes only, no URLs) and logged. An extension's cached history can then miss that change.
- Grants, earlier installs, revocation and private windows behave as for bookmarks; events are re-checked against the grant at every delivery. Query errors and denials reject the promise; the callback form logs and calls back with no argument (schema errors are not thrown synchronously as Chrome does).
- Events need the library hook (Arc owner) described in work/claude-history-hook-contract.md; until it is wired, search answers but no events fire.

### Where extensions can open tabs and windows

Bam honors an extension's requested target or refuses before anything is created; it never places a tab or window somewhere else. Little Bam windows hold one page and are reported as `popup` windows, and Peeks are marked as following the window's tabs (both need the integration flags applied); the browser window, which several profiles share, is `normal`.
- `windows.create` opens a Little Bam only for `type: 'popup'` with at most one URL. A `normal` window (Chrome's default when `type` is omitted) is refused: “Bam cannot open a new tabbed browser window for an extension. windows.create can open one page with type 'popup'.” `maximized` and `fullscreen` are refused; `minimized` is applied. Requested bounds that reach Bam (`left`, `width`, `height`, or `top` together with `height`) are refused (“Bam cannot place extension popups at requested bounds yet…”) until a real Little Bam round trip is proven: Little Bam has its own minimum content size, so applying a request could report bounds the extension did not ask for. Limitation: WebKit converts `top` using the requested height, so `top` alone arrives as “no bounds” and cannot be detected; such a popup opens at Little Bam's normal placement.
- `tabs.create` is refused for a popup window, another profile's window, or when WebKit resolves no window at all. WebKit resolves an omitted `windowId` to the current window, so this also refuses `tabs.create({url})` from a page in a Little Bam or from a worker while a Little Bam is focused. A new tab lands after this profile's tabs in the browser window, before any exposed Peek. Only that index is honored: an index before it is refused until a session seam can insert without changing a tab's folder or pin, and while a Peek is shown the default end index (which would count the Peek) is refused with the index that will be used. Without a Peek, omitted or past-the-end indices append.
- Session Buddy's restore into a new window therefore fails at `windows.create` instead of splitting one page into a Little Bam and the rest into the main window.

### Site access
Each extension's requested sites can be withheld, limited to specific sites or allowed in Manage Extensions › Site Access; Bam grants nothing an extension doesn't request. Withdrawing access restarts the extension, because WebKit otherwise keeps earlier content scripts and extension-page network access in its running pages; its own pages in Bam tabs reopen (page state is lost). A fresh context loaded while an old extension page is still alive would join the old web content process, which keeps the withdrawn site, so Bam loads it only after the old pages it can name (its tabs and previews of the extension, any popup WebKit asked Bam to present — shown or declined — and offscreen documents) have closed — WebKit-internal views and pages outside Bam aren't covered; if they don't close in time, Bam turns the extension off rather than keep that access; Enable brings it back once those pages are gone. If Bam also couldn't save that it's off, it is off only for now and may load again at the next launch. Isolated native fixtures at `52fdfae` observed such reads refused (a test page sending no CORS headers) after Site Access, Revoke, `permissions.remove` and expiry. The full native Extensions suite passed at `4ed2f83`, including these refusals; pages outside Bam that keep an old extension page alive can still keep its earlier access. Time-limited grants are noticed about a second after they expire, then the extension restarts. Storage survives a restart only in persistent profiles; private and other non-persistent stores reset. If the extension can't be stopped, Bam turns it off and asks you to quit and reopen Bam.

### Consent
Bam doesn't prompt for website access during an extension's calls. Tab reads proceed without the site; scripting, cookies and captures fail with WebKit's error. Cross-origin reads from the extension's own pages that need a site's host permission are refused for a site it never had. For a site it had and lost, they're refused once the restart described under Site access has completed (native Extensions suite at `4ed2f83`). A site's own CORS headers still decide what any page may read from it, extension pages included. Extensions regain a site through `permissions.request` (one review), a click on their toolbar button (activeTab), or Site Access. WebKit doesn't enforce Chrome's user-gesture rule for `permissions.request`. Safari-imported extensions follow the same rule and no longer ask per site.

### Tab addresses and titles (tabs permission)
For extensions holding `tabs`, the compatibility layer adds `url`/`title` to WebKit's own tab objects, matched by WebKit's tab ID under a native check that the tab layout didn't change; it grants no site. Several Little Bam windows, non-web pages and over-long values stay blank; events stay in order and may arrive up to about 1 s later with values at delivery; `favIconUrl` and `pendingUrl` aren't provided.

### windows.onBoundsChanged

WebKit has no `windows.onBoundsChanged`; Session Buddy 4.1.2 registers it unconditionally while its worker starts, so the missing event aborted its startup before it registered its action handler (root's canonical logs mapped the vendor's caught "Service worker error" to that call). Bam provides a working event, only where the engine lacks one. When a window the extension's profile exposes finishes moving or resizing (live resizes once they end; moves and programmatic changes after 0.3 s with no further change and no mouse button held), Bam signals that profile's extension pages and subscribed workers. The adapter then reads WebKit's own `windows.getAll()` and calls listeners with WebKit's Window object (its IDs and coordinates) for each window whose left, top, width or height changed since the previous read. Because each read compares every window, a committed signal is held while any window of the profile is in a live resize or a mouse button is down, and flushes once afterwards (reporting each changed window's final bounds). Opening or closing a window only refreshes which windows the baseline knows; it never reports and never overwrites a known window's geometry. Baseline and signals are serialized: a change committed before a new listener's baseline read completes becomes part of the baseline, and several changes between two reads are reported once with the final bounds. Windows that appear or disappear are not reported here (`onCreated`/`onRemoved`); a newly exposed window is added to the baseline. Windows of other profiles never signal. No permission is needed, as in Chrome. Canonical coverage at `483c54f`: the worker fixture verifies a shared window, a window exposed to one profile only, and a held live-resize seam; the extension suite passes 409 checks. The original Session Buddy 4.1.2 action then opens its main page, and a saved fixture collection survives page reload. Saved-link opening and physical pointer live-resize delivery remain unverified.

### declarativeNetRequest rules Bam refuses

WebKit does not validate `excludedResourceTypes`; a rule excluding every resource type WebKit supports (font, image, main_frame, media, other, ping, script, stylesheet, sub_frame, websocket, xmlhttprequest) becomes a rule with an empty type list, which matched an XHR in the canonical measurement — far broader than Chrome, where such a rule matches only types WebKit never sees. Bam refuses `updateDynamicRules` and `updateSessionRules` calls that add such a rule, before WebKit sees them, and never rewrites or drops a condition. The promise form rejects with “Rule with id N excludes every resource type this browser supports, so it would match all requests here.”; the callback form throws that error synchronously at the call (Bam cannot set `runtime.lastError`, so a callback without an error would look like success). Valid calls reach WebKit's method unchanged. Bam likewise refuses added rules with a non-empty `requestMethods` or `excludedRequestMethods` condition, whatever their action, with “Rule with id N has a request-method condition (requestMethods or excludedRequestMethods), which this browser does not enforce as written.” Canonical measurements with compiled-rule sentinels and independent server counts showed `requestMethods: ['get']` and `excludedRequestMethods: ['post']` rules blocking POST, and `requestMethods: ['post']` rules never blocking POST. Empty or malformed method values are left to WebKit's own validation. Static rulesets receive a bounded audit for disclosure only; the audit never changes their files or enabled state. The measured uBlock Origin Lite build’s enabled rulesets contain 16 method-conditioned rules (13 block, 2 allow, 1 redirect) that WebKit may apply differently from Chrome, and none excluding every type.

### Idle callbacks

On macOS 27.0.1, WebKit has neither `requestIdleCallback` nor `cancelIdleCallback` in a website's page, an extension's content-script world, or an extension page (measured in the canonical fixture). Proton Pass's injected `client.js` and uBlock Origin Lite's isolated scriptlets call them without a feature check. Bam defines both, only when neither exists, in the extension's own pages (after the page shim's origin check) and in the extension's isolated content-script world (Bam's prepended content adapter, which also reaches scripts injected later into that world). Callbacks run asynchronously in request order, each with a deadline of at most 50 ms. `didTimeout` (with no remaining time) is reported only when the requested timeout had already passed, and cancelled callbacks never run. These are timer-based, not tied to real engine idle periods. Service workers get nothing, as in Chrome. A website's own main world is never changed, so scripts an extension injects there (Proton Pass's `elements.js`, uBOL's MAIN-world scriptlets) still find the functions missing. Existing installs receive the new content adapter through the byte-exact adapter refresh, which recognizes each earlier Bam adapter generation and nothing else.

### Packaged WebAssembly

WebKit currently serves packaged `.wasm` resources with `application/octet-stream`, which breaks native streaming compilation. Bam adapts `compileStreaming` and `instantiateStreaming` only for a successful, readable response from the exact extension scheme and host with the wrong MIME. It passes those bytes to native compilation; imports, compile options, validation and CSP enforcement remain native. Foreign URLs, failed responses and normal WASM responses retain native streaming behavior. Bam does not weaken an extension’s CSP.

### Content-script messaging adapter

WebKit never invokes the callback of `runtime.sendMessage(extensionId, message, callback)` from a content script, while the promise form answers; vidIQ, Dashlane and 1Password content scripts all use the callback form, and vidIQ’s YouTube overlay never appeared until this was found. The importer prepends a small adapter file to every isolated-world content script list in the private copy. The adapter converts callback calls into the promise form (and keeps the runtime wrapper referenced so the patch survives WebKit’s weak wrapper cache); MAIN-world entries, CSS-only entries and all extension JavaScript are untouched, and the original manifest is saved outside the package when the MV2 step has not already done so. The review and manager disclose it. Its component suite covers the manifest rewrite, rejection of unsafe paths, coexistence with the MV2 preparation and, through JavaScriptCore, the adapter’s behaviour for two- and three-argument callbacks, rejections, synchronous results and promise pass-through; the native suite checks both callback forms against the real engine.

### Select-picker overlay compatibility

The 0.21.1 draft addresses Dashlane’s inline panel disappearing on pages containing a closed `<select>`. The tested WebKit exposes native `select:open` but returns an empty picker overlay style; Dashlane interprets the missing value as an open top-layer picker. Bam normalizes only empty `getPropertyValue("overlay")` reads on native style objects returned for an actual select’s exact `::picker(select)`, using the live native open state. The adapter is confined to isolated content-script worlds and disabled when overlay is supported or native open-state detection is absent. It preserves genuinely open picker detection, other styles, native errors and readonly behavior; it does not spoof CSS capabilities or rewrite vendor security checks. Existing packages refresh only Bam’s byte-exact legacy adapter. The helper passes 38 checks and content preparation/migration passes 51; the signed-in panel stays visible, and recreated standard/dynamic forms pass exact dummy-value checks. See [WebKit’s native open-state support](https://webkit.org/blog/17938/webkit-features-for-safari-26-5/) and [CSSOM pseudo-element style resolution](https://drafts.csswg.org/cssom/#dom-window-getcomputedstyle).

### Manifest V2 UTF-8 preparation

For a Manifest V2 package using background.scripts, the importer creates an explicit UTF-8 HTML background page in its private copy and replaces that scripts declaration with background.page. It retains the same external scripts in the same order, including module semantics and other background properties. Every JavaScript file remains byte-identical. The selected source folder stays untouched, and the original manifest is saved byte-for-byte outside the copied package as original-manifest.json. The import review and manager disclose the compatibility preparation. The helper accepts a manifest of at most 1 MiB, validates local relative script paths and regular files, rejects traversal/URLs/query fragments/symlinks, escapes HTML attributes, and chooses a unique generated filename. See WebKit’s [generated background page](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/Extensions/WebExtension.cpp) and [extension resource responses](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/Extensions/Cocoa/WebExtensionURLSchemeHandlerCocoa.mm).

Diagnostic arrays clear on unload/shutdown and each entry is limited to 1,200 Unicode scalars. A short lifecycle run cannot certify leak freedom or long-running vendor behavior.
