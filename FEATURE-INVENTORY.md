### Media and preview implementation boundary

A floating NSPanel containing a reparented WKWebView is an independent prototype implementation. It does not establish Arc’s internal PiP design, AVKit support, universal video extraction, DRM support, or cross-origin frame access. The acceptance tests above must use actual playing media, including delayed discovery and tab changes during asynchronous callbacks. A screenshot of a floating frame is insufficient. Prerelease 0.4.0 animates only an inert panel snapshot during Return; it does not resize the live video viewport. A bounded render wait and cleanup paths are source mechanisms, not proof of smooth rendering on every player.

Likewise, “persistent Peek” here means retained while its parent tab lives during the session. Restoring Peek navigation after app relaunch is a separate decision and is not claimed by the code inspected.

## Architectural prerequisites for Bam

These are engineering deductions from the inspected prototype and platform documentation, not recovered Arc source.

1. **Continue the versioned model beyond Spaces.** Session format 2 separates stable Space IDs from order. The local format-5 draft retains Favorite/kept metadata and sleep state, and adds profile IDs; it accepts session formats 1–5 and migrates legacy pins. Folder trees, broader activity and archive policy remain future model work; a compatibility `pinned` property alone is not the persisted retention model. [Current model][O-model]
2. **Define ownership of every live WKWebView.** Normal tab, Peek, Split pane, Little Bam and PiP need explicit transfers and cancellation. A view has one superview; promotion should transfer ownership rather than instantiate/reload. Controller callbacks must not resurrect closed tabs after asynchronous discovery. [Current PiP][O-pip], [Peek][O-peek]
3. **Choose profile/private storage before creating the view.** Apple provides named persistent data stores for profiles and nonpersistent stores for private sessions. Assign the store through configuration before constructing WKWebView. Grouping tabs visually is not cookie isolation. [Apple WKWebsiteDataStore][P-store]
4. **Build host services around WebKit.** History/archive, downloads, permissions, tab search and settings are browser-host work. Extension support additionally needs loaded contexts and browser tab/window adapters; Yab documents its own bridges for missing Chrome APIs. Merely embedding WKWebView does not add its advertised extension ecosystem. [Apple extension context][P-extension], [Yab extensions][Y-extensions]
5. **Keep commands surface-aware.** One command routing layer should resolve active normal tab, Peek, Split pane or Little Bam. Use it for address/find/zoom/reload/PiP instead of sending everything to the main tab. Restore focus and accessibility state after every overlay/window transition.
6. **Add durable data and cleanup deliberately.** Tab/session JSON is not history, downloads, credentials or sync. Separate stores and retention/deletion policies; use platform credential storage; private sessions should not be serialized. Recovery must tolerate interrupted writes and schema changes.
7. **Treat remote services as separate dependencies.** Sync needs key management/backend/device lifecycle; hosted sharing needs storage/access/deletion rules; AI/mail/live folders need provider authorization and explicit data boundaries. Those are separate systems, not capabilities supplied by a visual shell.

## Ordered implementation batches

Each batch ends with its acceptance criteria above exercised on a built app. Check boxes are not earned by file creation or compilation alone.

1. **Interaction correctness now — B02–B08, foundations of B01.** Verify the implemented automatic PiP and return, view transfers, retained per-tab Peek, Little Bam/external delivery, and two-pane Split against cancellation and ownership races. Test the same live page through normal → Peek → tab/Split/Little → PiP and back, plus close/navigation during transitions. Automatic app-occlusion PiP and four-pane Split may remain explicitly deferred.
2. **Durable tab and Space semantics — T02–T07, T11.** Migrate schema; true Favorites vs kept tabs; original URLs; create/edit/move Spaces; folders/reorder/undo; persist Split pairs. Retain profile IDs and explicit sharing across later UI changes. Prove old sessions and invalid-reference fixtures still load.
3. **Everyday navigation — N01–N04, N08, T04.** Extend the existing tab palette and per-surface find/zoom/print with command actions, MRU navigation, configurable engines/site search, settings and routing rules. Little Bam routing consumes the stable Space/profile identities from batch 2.
4. **Browser data and files — T08–T10, N05–N07.** Extend durable visit/closed-record storage and session downloads with archive policies/exemptions, sleeping, download resume/retry, richer Library, link/capture/export, and user-selected import. Do not conflate Clear History, Close Tab, Archive and Delete Download.
5. **Isolation and safe host integration — B09, T06, S02–S06, S08.** User-facing private/profile windows, data deletion, permissions/authentication, blocker, developer tools, credential providers, then extension host integration. Establish profile isolation before importing secrets or enabling extensions. This batch can start in parallel with batch 3 after the model/storage boundary is stable.
6. **Personalization and portability — T01 remaining, S01, S07, S09–S11.** Theme editor, Boosts, live folders, reader/page tools; then sync/sharing if desired. Treat live service compatibility and security review as explicit work. Easels are optional scope, not browser-core completion.
7. **Yab-specific product expansion — S12–S13.** Agents/MCP/CLI, routines, mail/calendar/snippets and launcher utilities. Separate milestones and acceptance tests; these substantially exceed an Arc-style native browser shell.
8. **Release readiness — S14, all previous critical paths.** Signing/notarization/updater, accessibility audit, fixture-based and representative live-site testing, resource measurements and documented limitations. Re-run this inventory against the shipped commit and update each status with test evidence.

### Definition of an honest milestone

“Arc-inspired native prototype” is supportable before broad parity. “Daily-use browser” requires the ordinary navigation, download, permission, session-recovery and security behaviors. “Arc/Yab parity” requires a stated feature subset and compatibility matrix; neither a successful build nor a similar-looking interface establishes it.
